Manage Connectors V2
Proposal · August 2026
The whole idea
Unify the connector interface into one card system with clear sections.
Today, connectors appear in two different places and look different: a table on the main page and cards in the Explore dialog. This redesign combines them into one unified card system with two clear sections: "Connected" (connectors you're already using) and "Available to connect" (what you can add). We're implementing this in stages: clean up the data layer, fix logo display, introduce the card design, and fix pagination so the screen requests one page at a time instead of downloading everything on open. We won't claim certainty about information that's incomplete or synthesized in the backend.
Why we're making this change
Two connector UIs in one codebase; designs expects one interface
Maintaining two rendering systems means every fix—loading states, empty states, hover behavior—gets built and tested twice, and the two have already drifted apart in small ways. The design's two-section layout is built entirely from cards, so keeping the table means retrofitting grouping onto a component that was never built for it. Consolidating removes the duplicate work and matches the structure the design actually calls for.

Today

  • Single flat list with a status badge on each row
  • Explore dialog uses a different card style in a different place
  • No clear visual distinction between connected and available
  • Duplicate code for empty/loading states in two places

After the redesign

  • Two clear sections: "Connected" and "Available to connect"
  • One card design, used everywhere
  • Same cards adapt to different screen sizes (narrow to wide)
  • One code path for loading and empty states
Things to watch out for Data fidelity

Connector Gateway does not provide an enabled field

The Connector Gateway responses do not contain enabled. The frontend compatibility adapter synthesizes enabled: true for each adapted profile, so this value must not be treated as backend state. When the legacy MCP Gateway path is used, its response does include enabled; that is a legacy compatibility field, not part of the Connector Gateway contract. The Connected/Available split doesn't rely on either field. Instead:

  • Connected: The connector has a profile in the merged list (real data from either backend)
  • Available: The connector exists in the catalog but this user has no profile for it yet

This check works the same way other parts of the codebase already handle it — by asking "does this user have a relationship to this connector?" rather than reading a status flag. So the layout is built on real data and safe to ship. The fabricated enabled field is dead code in the adapter and shouldn't be relied on for anything.

Why enabled exists at all: it's a legacy compatibility field, present only to satisfy the shape of the old UserProfileConnector object that some older code still expects. It has no real purpose in V2 — nothing in this design reads it, and no live code path depends on it being accurate. If a clean break from the legacy shape becomes possible, the adapter's enabled field can be dropped entirely; until then it's kept only for callers we haven't audited.

How to build it
Pick the right strategy for the implementation
We have several ways to build this redesign. Each approach trades off risk, speed, and complexity differently. Here are the main options. Every option ships behind a feature flag — that's not a differentiator between them, see the Release Plan below for details.

A — Build separately

New card page built alongside the old one. Delete the old page after it's verified.

Cost: two live versions for a while; most problems surface at once when the flag flips.

B — Reshape step by step

Gradually turn the current table into the new card design, one piece at a time.

Cost: table and cards are organized too differently — every in-between step ships a confusing half-old, half-new page.

C — Same engine, swap the display

One shared engine for data/clicks/permissions; only the row-vs-card drawing swaps.

Cost: only works if table and card can share the exact same data — and today's data has known gaps, so this can quietly turn into A anyway, just discovered later.

Recommendation: Option A

C's data assumption doesn't hold today, so it risks becoming A anyway, later and with less warning. B ships a confusing half-old, half-new page at every intermediate step, with no way to hide that behind a flag. A gives a clean side-by-side comparison before launch and one clean cleanup step after — at the honest cost of running two versions until the flag flips.

Technical approach
Cards instead of a table
Replace the table with cards organized into "Connected" and "Available to connect." The two sections are a presentation choice, not a claim that every connected profile is healthy or usable. Each card shows the connector name, a logo (properly loaded), its applicable state, and only the actions the user can take. The cards rearrange based on screen width: more columns on a wide screen, fewer on a phone. Today, one 639-line component (connectors-tab.tsx) handles everything — fetching data, search, sort, pagination, and nine different pieces of modal/dialog state. We're splitting that into four focused pieces: fetching data, organizing the list, handling actions/dialogs, and displaying it.
Profile states within the two-section UI Product contract

Decision: keep exactly two page sections. Connected means an applicable connector profile exists; it does not imply the profile is enabled, authorized, or currently usable. Available to connect means no applicable profile exists. Health, ownership, authorization method, and permission determine the card treatment inside those sections; they do not create additional sections.

SectionProfile conditionCard treatmentPrimary action
ConnectedActive and healthyConnected status; show ownership/default metadata when applicableManage
ConnectedDisabled or turned offOff status; keep the existing profile visibleTurn on, if permitted; otherwise Manage
ConnectedAuthorization expired or connection errorNeeds reconnect/error status; do not imply the connector is usableReconnect, if permitted; otherwise show the actionable owner/context
ConnectedOrg-level profileShared/org ownership label; actions respect org permissionsManage org connection, when permitted
ConnectedUser-level profilePersonal ownership labelManage my connection
Available to connectNo applicable profileAvailable stateConnect

Auth route changes the connection or repair flow, not section placement: code_grant uses the OAuth/reconnect path; api_key and http_basic use their credential flows. The card must not present an OAuth-specific action for a credential-based connector, or vice versa.

Calendar proof case: an existing Calendar code_grant profile stays in Connected. When healthy, it exposes its normal management action; when its authorization expires, the same card changes to “Needs reconnect” and exposes the OAuth reconnect flow. It never moves to Available solely because it is broken or disabled.

Dependent behavior guardrail: this page rewrite must preserve the Chat connector dropdown’s current eligibility and selection behavior for each profile type and state. Chat is not being redesigned, but its assumptions must be identified and covered by regression scenarios before rollout.

Reads the feature flag, fetches connectors, checks permissions, and owns logo URLs and enable/disable/revoke actions. Owns the search box, sort order, and current page number. It doesn't fetch — it tells the data hook which page to request. This fixes today's bug where the page silently downloads everything and slices it locally instead of asking the backend for one page at a time.

Dialog states and transitions Frontend

The page has two dialogs: Details (search and browse connectors, or drill into one for preview/connect) and Connect (add to agent). Only one is ever open at a time. The modal orchestration hook owns both and the consent flow. Rather than one diagram for everything, here are the three things that actually happen: which dialog opens, what happens if the user hasn't given consent yet, and how a connect attempt ends.

1. Opening a dialog. Details opens directly for browsing. Clicking Connect from anywhere is the only thing gated on prior consent acceptance.

3. How a connect attempt ends. Once the Connect dialog is open and OAuth (or an API key) is submitted, there are only two outcomes.

Where this lives: The orchestration hook (use-connectors-modal-orchestration.ts) owns which dialog is open and the pending consent intent in Jotai atoms. Per-card pending flags (loading, error) for add/remove actions are separate atoms, keyed by connector ID.

State ownership map Frontend

Three stores, three jobs, no overlap:

  • Server data — React Query (@tanstack/react-query ^5.75.2). Connectors, profiles, agent config, signed logo URLs. Never mirrored into a client store.
  • URL — search term and sort field/direction, so a filtered view is shareable and survives reload. This is a change from today, where both live in component useState. The app is Next.js 16, so this is useSearchParams plus a shallow replace, not a new dependency.
  • Ephemeral UI — which dialog is open, which row menu is expanded, the pending consent intent, per-card pending/loading flags. This is where the state-library choice matters; see below.

Ephemeral UI state: zustand vs. Context vs. Jotai

OptionFit for this page
React ContextAny value change re-renders every consumer unless the tree is manually split into narrow providers. With N connector cards each holding their own menu/pending state, that's either one re-render storm or a lot of hand-rolled provider nesting. Not chosen.
zustandCodebase standard (^5.0.3, 41 files, including frontend/src/stores/connectors-flow.ts, which already covers this page's flow state). One shared store; avoiding over-rendering requires disciplined selectors per component. Works, but doesn't fit the "many independent per-card slots" shape especially well.
Jotai (chosen)Atomic by default — each piece of state is its own atom, so a component subscribed to one card's menu-open atom never re-renders when another card's atom changes. atomFamily keyed by connector/profile id gives exactly the "which row is this" shape this page needs (open menu, pending-add, pending-remove) without hand-writing per-id selectors. Trade-off: net-new dependency, zero existing usage in this codebase, so the team pays a one-time learning/setup cost.

This page uses Jotai for its ephemeral UI state — a deliberate, scoped exception to the zustand-everywhere norm, not a general replacement. connectors-flow.ts keeps owning the flow state it already has; Jotai only covers the new card layout's per-item state (menu open, pending add/remove).

Data loading and progressive rendering Backend

Current behavior

The page already loads connectors a page at a time and shows them as soon as the first page arrives — it doesn't wait for everything. ConnectorsTab renders as soon as page one lands, keeps fetching more pages in the background, and shows the notice "Loading more connectors. Search results may be incomplete." while that's happening. It also already handles the first load, the in-progress load, and a later page failing separately.

What the redesign must do

Preserve, not rebuild. The progressive-render behavior is an existing invariant to carry across the rewrite and pin with tests: page one renders before page two resolves, the partial notice appears during drain and disappears after, and a page-two failure keeps page-one rows with a working retry. The risk in a decomposition is silently regressing this into a blocking spinner.

Server-side pagination — already built, just bypassed

Confirmed in code: the backend already does real paging, and the frontend already has a working query (useListUnifiedUserProfiles) that requests it with a real limit/offset. Nothing needs to be added on the backend.

The bug is a frontend one: an effect in connectors-tab.tsx (lines 250–256) automatically calls fetchNextPage the moment each page arrives, looping until every connector has been pulled into the browser. The on-screen "pages" then come from slicing that one giant downloaded array locally — the real offset the query supports is never used to ask for just the page the user is looking at.

This redesign must fix that effect so the screen requests one page at a time using the offset that already exists, instead of draining everything on open. No new API contract needed — this is a frontend fix, not backend work.

Observed six-request cascade in the Connector Gateway path

Observed in the Network panel and confirmed in code: the six profile requests are three org-profile pages (offset=0, 100, and 200) plus the same user-profile request repeated after each one. ConnectorsTab's auto-drain effect immediately calls fetchNextPage while hasNextPage is true. Each infinite-query page invokes fetchUnifiedUserProfilesPage, which starts both requests: the org-profile request uses that page's offset, while the user-profile request is reset to offset=0&limit=1000.

Infinite-query pageOrg profiles requestUser profiles request
0offset=0&limit=100offset=0&limit=1000
100offset=100&limit=100offset=0&limit=1000 — duplicate
200offset=200&limit=100offset=0&limit=1000 — duplicate

This is not a TanStack Query cache miss: the repeated user request is made inside the paged query function, outside the cache's request-deduplication boundary. The cascade is a second, independent problem: the page asks for all org pages on mount. Replace this shape with two independent, organization/team-keyed initial-load queries: one org-profile request at offset=0&limit=100 and one user-profile request at offset=0&limit=1000. Merge their cached results for rendering. Remove the auto-drain effect; a later org page may be requested only by an explicit pagination/load-more interaction. Initial page load must therefore make exactly those two profile requests.

The same cascade re-fires on every connect and disconnect

Confirmed with a fresh HAR capture, not just the initial-load trace above: connecting or disconnecting a profile re-triggers the identical six-request cascade — it isn't limited to first paint. invalidateConnectorProfileQueries (frontend/src/hooks/react-query/mcp-gateway/use-gateway.ts, lines 561–585) is the shared invalidation helper called by useConnectCgProfile, useDisconnectCgUserProfile, useCreateOAuthProfileMy, useDeleteProfile, and useUpdateCgUserProfile. It unconditionally invalidates the unified-profiles infinite query (getUnifiedProfilesV3QueryKey) among others. Invalidating an infinite query tells TanStack Query to refetch every page that is currently loaded, not just the first — so once the auto-drain effect above has pulled in all three org pages, any one of these five mutations re-runs the full three-page-plus-duplicate-user-request cascade again.

TriggerRequests observed immediately after
POST .../profiles/{id}/connectorg offset=0, org offset=100 + duplicate user offset=0&limit=1000, org offset=200
POST .../profiles/{id}/disconnectorg offset=0, org offset=100 + duplicate user offset=0&limit=1000, org offset=200

The fix above (two independent initial-load queries, auto-drain effect removed, later org pages fetched only on explicit load-more) resolves this for free: with only page one ever loaded by default, invalidating the infinite query after a mutation refetches just that one already-loaded page instead of redraining everything. No separate fix is needed for the mutation path — it inherits the pagination fix. The acceptance criteria below should be read as covering both the initial load and every subsequent connect/disconnect, not initial load alone.

Logo resolution and signing contract Frontend

The problem

Custom connector logos are stored as logo_… paths. They require signing via useResolvedLogoUrl before <img> can render them. The Manage Connectors table today uses logoUrlMap[path] ?? rawPath, which can send unsigned paths to the image element. This is a bug that the redesign should fix.

The contract

Use the existing resolveConnectorLogo resolver (or equivalent shared function) so:

  • Built-in connector URLs pass through unchanged
  • Custom paths are resolved via the ['signed-logos', orgId, [sortedPaths]] query
  • Signing in-flight or missing org scope returns undefined, not a raw path
  • Fallback is the existing connector plug icon

Normalize this behavior in the data hook (step 2) before the card layout lands, so the shell never handles raw storage paths. Note the ordering dependency: ConnectorCard currently takes logoUrl as a prop and falls back to connectorApp?.logo — so any shared card must receive an already-resolved value, never resolve one itself.

Connector Gateway adapter fidelity gates Data fidelity

What is lossy

Fields affected by the frontend adapter:

  • enabled — not returned by CG; synthesized as true for legacy-shape compatibility
  • totalToolCount — derived from tool list length; unreliable without explicit count
  • provider — available only for MCP_REMOTE tools; guessing for others
  • Tool schemas, annotations, tags, ownership, tenant modes — all dropped
  • Timestamps, creation metadata — dropped
  • Custom logo paths — present but require signing before use

The gate

Any design requirement that depends on one of these fields must first resolve:

  • Use a field marked GO (preserved with no loss)
  • Define a parallel CG-native view model that owns the field natively
  • Add an explicit, backend-owned contract that enriches the legacy shape

This keeps the design honest about what's trustworthy and prevents silent failures when CG values change or are unavailable.

The Connected/Available split does not use the invented enabled field. It works the same way two other places in the codebase already do it: project-settings-connectors.tsx splits "Added" vs. "Available" by whether the connector is on that project's list, not by any status field. The Explore catalog does the same — a connector counts as connected simply because it has a profile, not because of a true/false flag.

The redesign follows that same pattern: "Added" means the connector has a profile in the merged list; "Available" means it's in the catalog but has no profile yet. That check works the same in both flag states, so there's no data-fidelity problem blocking step 5.

Questions to settle
Design decisions to make before coding

1. Decided — keep both Explore and the new "Available to connect" section

The Figma design doesn't show the Explore modal being replaced. Explore stays as the place to browse and add brand-new connectors; the "Available to connect" section on the main page is for connectors the org already offers but this user hasn't turned on yet.

2. Decided — sort by name only, for now

Name (A to Z) stays the only sort option. The Figma design doesn't show a sort-by-date or sort-by-status control. Add one later if users ask for it.

3. Decided — one column on very small phones

The design covers down to 640px width as one column. Below that, we keep one column rather than adjusting further.

4. Decided — build a new Connect dialog

The Figma design shows three purpose-built states for the Connect dialog (connecting, success, failure) that don't match the current generic connect dialog. Build these as new components rather than restyling the old one. This applies only to Connect — Explore and Preview are unchanged, only their trigger wiring moves.

5. Still open — first-time setup dialog

Figma shows a setup dialog for new users. Where we store "this user has already seen it" is still to be confirmed — leaving this open for now.

6. Decided — initial load makes two profile requests, not six

Network trace: the six requests are three sequential org pages and three copies of the same user-profile request. Cause: the auto-drain effect starts page 100 and page 200 on mount, and each page's query function also reads the unpaged user profiles. A follow-up HAR capture confirms the same six-request cascade re-fires on every connect and disconnect too, because invalidateConnectorProfileQueries invalidates the infinite query and TanStack Query refetches every already-loaded page. Decision: use separate org and user queries, merge their cached results, and remove auto-drain. On initial load, make exactly one org-profile request (offset=0&limit=100) and one user-profile request (offset=0&limit=1000). Request later org pages only after an explicit user-driven pagination/load-more action. Because only one page stays loaded by default, a later connect/disconnect invalidation refetches that one page instead of redraining everything — no separate fix needed for the mutation path.

7. Decided — fix pagination to request one page at a time

Required. The backend and the query layer already support real paging with a working limit/offset — no new backend contract needed. The bug is a frontend effect (connectors-tab.tsx:250-256) that auto-fetches every page on open and then slices that full array locally. This redesign must remove that drain-everything effect and have the screen request only the page it's showing. Nothing is open here; this is a scoped frontend fix.

Scope
What's included and what's not
This redesign focuses on the connector page interface: the new card layout, fixing how data flows through the page, and improving logo display. It does not include changes to the backend, design system, or other parts of the product that happen to use the same icons or components.

Included

  • Redesigned profiles list: new card layout, status badges, and responsive sizing
  • New Details modal: consolidates search, browse, and preview into one screen (replaces separate Explore and Preview dialogs)
  • New Connect dialog: three purpose-built states (connecting, success, failure) replacing the current generic connect dialogs
  • Unified data fetching: org profiles and user profiles merged cleanly
  • Isolated state: per-card UI state separate from data
  • Pagination fix: fetch one page at a time instead of draining all pages upfront
  • Connector Gateway duplicate-fetch fix: cache the user-profile read separately from paged org-profile reads
  • Logo handling and name-only sort

Not included

  • Design system changes or new components
  • Changes to other pages or unrelated parts of ConnectorsTab
  • Setup dialog storage mechanism (TBC)
